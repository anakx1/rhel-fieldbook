An application can be running but not listening where you expect. ss is the modern socket inspector:

terminal · listening sockets
ss -tulpn
ss -tan state established
ss -tlnp | grep :22

-t TCP, -u UDP, -l listening, -n numeric ports, -p process. The process column requires privilege for sockets owned by other users. A service bound only to 127.0.0.1 will not accept remote connections even if the port is open locally.

DNS is a frequent culprit. Test resolution separately from reachability:

terminal · resolution and reachability
getent hosts server.example.com
cat /etc/resolv.conf
ping -c 3 192.0.2.50
curl -I http://server.example.com

getent hosts uses the system's name service switch, which is what applications actually use. dig or host queries DNS directly but may not reflect /etc/hosts or other name service sources. Test with the same mechanism the application uses.

ping proves ICMP reachability, not application health. A host can block ICMP and still serve HTTP. curl -I checks the application layer; ss checks the listener; ip route checks the path. Use the layer that matches the symptom.
