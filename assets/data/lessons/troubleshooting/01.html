Under pressure, the temptation is to try the last thing that worked on a different system. Resist it. A short method keeps you from turning one problem into three.

  1. Define the symptom — what is broken, for whom, and since when? "The site is down" is not a symptom. "HTTP 502 from the load balancer since 09:12 for all users" is.
  2. Establish scope — one host or many? One service or the whole platform? One network or every network?
  3. Find the timeline — what changed just before? Package update, config change, certificate expiry, DNS change, disk growth, deploy.
  4. Collect evidence — logs, status, capacity, network, process state. Preserve before you restart.
  5. Form one hypothesis — the smallest explanation that fits the evidence.
  6. Test one change — then observe. If it did not help, revert before trying the next thing.
Restarting destroys evidence

A restart may restore service, but it also clears the state that explains the failure. Capture systemctl status, logs, and resource state first whenever it is safe to do so.
