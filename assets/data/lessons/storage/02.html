Temporary mounts are useful for inspection and recovery. Persistent mounts belong in /etc/fstab, and the safe way to reference a filesystem is by UUID, not by a device name that can change.

terminal · mount by UUID
sudo mkdir -p /mnt/data
sudo blkid /dev/sdb1
sudo mount UUID="8f3c1e2a-..." /mnt/data
findmnt /mnt/data
sudo umount /mnt/data

If umount reports "target is busy," find out what is using it before forcing anything:

terminal · who is using the mount?
sudo lsof +D /mnt/data
sudo fuser -vm /mnt/data

A common cause is a shell whose current directory is inside the mount. cd out, close the process, then unmount. umount -l (lazy) and umount -f (force) exist, but they are recovery tools, not first choices.

/etc/fstab fields
UUID=8f3c1e2a-...  /data  xfs  defaults  0 0

The six fields are: device, mount point, filesystem type, options, dump flag, and fsck pass. On XFS, the sixth field is typically 0; XFS does not use the traditional fsck pass model in the same way as ext4.

Test fstab before rebooting

A typo in /etc/fstab can drop the system into emergency mode. Run sudo mount -a after editing; if it succeeds without error, your syntax and UUID are at least plausible. Keep console access.
